Introduction
The Ride-Sharing Trust Problem
Centralized cab-sharing platforms rely on a single point of trust — the platform operator — to mediate identity, disputes, and data privacy.
⚠️

Risks in Centralized Systems

  • Single point of failure — server compromise leaks all user data
  • Opaque dispute resolution — users cannot verify fairness
  • Identity manipulation — fake accounts, unverified drivers
  • Data monetization — location history sold to third parties
  • No accountability audit — ride records can be silently modified
🔗

What Blockchain Brings

  • Decentralized trust — no single authority controls outcomes
  • Immutable records — tamper-evident ride lifecycle events
  • Transparent governance — on-chain voting for disputes
  • Privacy by design — encrypt-first, reveal-selectively
  • Cryptographic verification — prove facts without exposing secrets

How can we design a peer-to-peer carpooling system for a campus environment that provides verifiable trust, privacy-preserving identity management, tamper-evident ride operations, and decentralized dispute resolution — without relying on a centralized intermediary?

Hybrid Design Rationale

Off-chain (MySQL): Full application state for performance, search, and privacy — avoids storing PII on a public ledger.
On-chain (Blockchain): Tamper-evident hashes, ride lifecycle events, dispute anchoring, and governance — provides integrity proofs. Blockchain calls are best-effort: if the chain is temporarily unavailable, the app continues functioning and retries when possible.

Cryptographic Primitive 1
Soulbound Tokens (SBT) — Academic Identity

What are Soulbound Tokens?

Non-transferable NFTs proposed by Vitalik Buterin (2022). Once minted to a wallet, they cannot be sold, traded, or moved — they are permanently bound to the soul (wallet address).

How We Use SBT

  • User registers with @iiitkottayam.ac.in email
  • Email verified via OTP (Resend API)
  • On verification, admin mints SBT via UserIdentity.mintStudentSBT()
  • SBT proves the user is a verified IIIT student

Security Properties

  • Sybil Resistance — 1 person = 1 verified SBT
  • Non-Transferable — prevents account selling
  • Privacy Preserving — only stores verification status, not PII
  • Permanently On-Chain — academic credential persists
// UserIdentity.sol — SBT Minting mapping(address => bool) public hasStudentSBT; function mintStudentSBT(address student) external { require(msg.sender == admin, "Only admin"); require(!hasStudentSBT[student], "Already minted"); hasStudentSBT[student] = true; emit SoulboundTokenMinted( student, block.timestamp ); } // Non-transferable by design: // No transfer() function exists

Contract: UserIdentity.sol

~120 LOC • Stores user profiles (username, email, IPFS hash) + SBT status • 5 events for complete audit trail

Cryptographic Primitive 2
Zero-Knowledge Proofs — Driver Verification

The Zero-Knowledge Paradigm

Introduced by Goldwasser, Micali & Rackoff (1985). A ZKP allows a prover to convince a verifier that a statement is true without revealing any information beyond the validity of the statement.

Three properties: Completeness, Soundness, Zero-Knowledge.

Application: Driver Credential Verification

  • Driver has private inputs: license number, expiry date, registration
  • Generates ZK proof: "I have a valid license"
  • Contract verifies proof on-chain
  • License number never revealed to platform or riders

Smart Contract

ZKPDriverVerifier.sol (~30 LOC) — Mock verifier. Production would use Groth16 or PLONK proof systems. Stores isRideZKVerified[rideId] flag on successful verification.

↓ generates proof
ZK Proof + Public Signals
proof = ZK.prove(private, statement)
↓ submits to chain
ZKPDriverVerifier Contract
verifyDriverZKProof(rideId, proof, signal)
↓ result
✓ Driver Verified
Credentials NEVER revealed
Cryptographic Primitive 3
ECDSA Signatures — Cryptographic Boarding Pass

Boarding Verification Problem

How does a driver cryptographically verify that the correct passenger is boarding, without relying on a centralized server to mediate?

Our ECDSA Solution

  • Rider signs message: keccak256(rideId, driverAddress, "BOARDING_PASS")
  • Rider shares the 0x-prefixed signature with driver
  • Driver submits signature to boardRider() on-chain
  • Contract recovers signer via ECDSA.recover()
  • If recovered address matches rider's wallet → boarding confirmed

Uses OpenZeppelin

ECDSA.sol + MessageHashUtils.sol for secure signature recovery. Prevents signature malleability attacks.

// RideContract.sol — boardRider() function boardRider( uint256 rideId, address rider, bytes memory signature ) external rideExists(rideId) onlyDriver(rideId) { // Reconstruct expected message bytes32 msgHash = keccak256( abi.encodePacked( rideId, msg.sender, "BOARDING_PASS" ) ); // Convert to Ethereum signed hash bytes32 ethHash = MessageHashUtils .toEthSignedMessageHash(msgHash); // Recover signer from signature address signer = ECDSA.recover( ethHash, signature ); // Verify rider is the actual signer require(signer == rider, "Invalid boarding signature"); // Mark rider as boarded emit RiderBoarded(rideId, rider); }
Cryptographic Primitive 4
DPoS Governance — Decentralized Dispute Resolution

Delegated Proof of Stake (DPoS)

Proposed by Daniel Larimer (2014). Uses a two-stage process: stakeholders elect a validation committee by voting proportional to stakes, then the committee acts on behalf of the community. Used in EOS, Lisk, Tron.

Our Implementation

  • Candidate Registration: Anyone stakes ≥ 0.01 ETH to become a candidate
  • Voting: Users vote (payable) for candidates they trust
  • Delegate Selection: Top 5 candidates by total votes = active delegates
  • Dispute Voting: Only delegates can vote Approve/Reject on disputes
  • Quorum: 3 out of 5 delegates needed for valid outcome
  • Time-Bound: 24h voting period, auto-finalize on expiry

Dispute Lifecycle

1. User files complaint with evidence
↓
2. openDispute(rideId, evidenceHash) on-chain
↓
3. Delegates review & vote (24h window)
↓
4. Quorum reached → Auto-finalize
↓
5. Outcome enforced (on-chain record)

Two Smart Contracts

DPoSGovernance.sol (~160 LOC): Candidate registry, voting/unvoting, top-N delegate computation.
DisputeResolution.sol (~115 LOC): Cross-contract onlyDelegate modifier, quorum logic, time-bound finalization.

Cryptographic Primitive 5
Merkle Trees — Verifiable Audit Trail

Merkle Trees in Blockchain

Invented by Ralph Merkle (1979). A binary hash tree where each leaf is the hash of a data block. The root hash is a fixed-size commitment to the entire dataset. Used in Bitcoin, Ethereum, Git, IPFS, and Certificate Transparency.

Our Implementation

  • Batch anchoring: Admin batches N rides → builds Merkle tree → anchors root on-chain
  • Verification: Prove any single ride existed with O(log n) proof
  • Storage efficient: Only 32-byte root stored on-chain per batch
  • IPFS metadata: Full batch data stored on IPFS, root on-chain

Cryptographic Primitive 6
CP-ABE — Ciphertext-Policy Attribute-Based Encryption

What is CP-ABE?

Proposed by Bethencourt, Sahai & Waters (2007). In CP-ABE, data is encrypted under an access policy (e.g., "host OR accepted_passenger"). Only users whose attributes satisfy the policy can decrypt. Unlike traditional encryption (encrypt for ONE person), CP-ABE encrypts for a set of roles.

Application in D-CARPOOL

  • Vehicle info (plate number, color) encrypted with policy:
    "ride_456_host OR ride_456_accepted"
  • Host gets key with attribute [ride_456_host]
  • Accepted rider gets [ride_456_accepted]
  • Random users → cannot decrypt
  • Leaving ride → attribute revoked → access revoked

Traditional vs CP-ABE

AspectTraditionalCP-ABE
Encrypt for1 personPolicy/roles
New user accessRe-encryptAuto (if attributes match)
Access controlKey per userAttributes per user
ScalabilityO(n) keysO(1) ciphertext

Implementation

cpabe_service/ — Flask microservice (port 7001) providing encrypt/decrypt/keygen endpoints.
Server-side: cpabeClient.js, cpabeHelpers.js, cpabeKeyStore.js — transparent integration with ride creation/viewing. Best-effort: if CP-ABE service is down, falls back gracefully.

Cryptographic Primitive 7
Shamir's Secret Sharing — SOS Emergency Data

Shamir's Secret Sharing (1979)

By Adi Shamir. Splits a secret $S$ into $n$ shares using a random polynomial of degree $k{-}1$ over a finite field. Any $k$ shares can reconstruct $S$ via Lagrange interpolation. With $k{-}1$ or fewer shares, zero information about $S$ is revealed.

This is information-theoretic security — unbreakable even with unlimited computing power (unlike encryption which is computationally secure).

Mathematical Foundation

Secret $S = a_0$. Choose random $a_1, ..., a_{k-1}$.
Polynomial: $f(x) = a_0 + a_1 x + a_2 x^2 + \cdots + a_{k-1} x^{k-1} \pmod{p}$
Shares: $(i, f(i))$ for $i = 1, ..., n$
Recover: $S = f(0) = \sum_{j=0}^{k-1} y_j \prod_{m \neq j} \frac{x_m}{x_m - x_j}$

SOS Emergency Data (5,3) Scheme

Emergency Data: {contact, blood group, allergies}
↓ Shamir Split (n=5, k=3)
Share 1 → Admin
Share 2 → User Wallet
Share 3 → Trusted Contact 1
Share 4 → Trusted Contact 2
Share 5 → Blockchain Backup
↓ SOS Triggered — collect 3 shares
✓ Reconstruct → Emergency services notified

Smart Contract: ShamirSOSVault.sol

~355 LOC (largest contract) • configureSOS() — set threshold scheme • commitShare() — on-chain hash commitment • triggerSOS() — emits GPS coords • verifyShare() — keccak256 comparison • Threshold tracking per event

Observations

Merkle root anchoring is the most gas-efficient bulk operation — stores unlimited rides with a single 32-byte root. ECDSA boarding verification (~65k gas) is cheaper than a typical ERC-721 transfer (~100k gas), making it practical for per-ride use on testnet.

On-Chain vs Off-Chain Data Strategy

Stored Off-Chain (MySQL)

  • Full user profiles (name, email, phone)
  • Ride details (locations, times, seats, vehicle)
  • Participant status and join history
  • Complaint descriptions and evidence
  • SOS alert details and contacts
  • Rating comments

Why?

Performance (indexed queries), privacy (no PII on public ledger), storage cost (0-cost vs. gas per byte)

Stored On-Chain (Blockchain)

  • SBT verification status (bool per address)
  • Ride lifecycle events (Created, Started, Completed)
  • Agreement hash (32 bytes per ride)
  • Rating scores (running average)
  • Dispute records + delegate votes
  • Merkle root per audit batch (32 bytes)
  • SSS share commitments (hashes only)
  • ZKP verification flags

Why?

Immutability, tamper-evidence, public verifiability, non-repudiation, trustless governance

Future Work
Limitations & Future Directions

Current Limitations

  • ZKP: Currently a mock verifier — production needs zk-SNARKs (Groth16) or PLONK with circuit compiler (Circom)
  • Gas Costs: Testnet (free) — mainnet deployment requires L2 optimization (Polygon, Arbitrum)
  • CP-ABE: Python mock service — production needs C-based library (libbswabe) for performance
  • Scalability: Not tested with 1000+ concurrent users
  • Mobile: Web-only — no native mobile app

Future Directions

  • Real ZK-SNARK Circuit: Circom + snarkjs for driver license proof (age ≥ 18, license validity)
  • Layer 2 Deployment: Polygon zkEVM or Arbitrum for sub-cent gas costs
  • Decentralized Identity (DID): W3C DID standard integration
  • Cross-Campus Federation: Multiple campuses with federated identity
  • Formal Verification: Certora / Slither for smart contract correctness proofs
  • Mobile App: React Native with WalletConnect
  • Tokenomics: Ride reward tokens for sustainable incentive design
