# D-CARPOOL — Blockchain Work Done (Detailed)

This document explains **what blockchain features were implemented in this project**, how the smart contracts are structured, how deployment works on **local Hardhat**, and how the **backend anchors critical actions on-chain**.

---

## 1) Why Blockchain Was Added

Blockchain is used to add **integrity, transparency, and auditability** for actions that are typically easy to manipulate in centralized systems.

In D-CARPOOL we follow a **hybrid model**:
- **Off-chain (MySQL DB)** stores the full application state for performance and privacy.
- **On-chain (Hardhat smart contracts)** stores **tamper-evident events / references**:
  - ride start/completion markers
  - dispute creation with evidence hash
  - (optionally) reputation/rating proof

---

## 2) Blockchain Environment (Local Hardhat)

### Network
- Development network: **Hardhat localhost**
- RPC URL (backend uses): `http://127.0.0.1:8545`

### Deployment
- Contracts are deployed using Hardhat deploy script:
  - `contracts/scripts/deploy.js`

### Outputs produced by deployment
Deployment generates:
- **Contract addresses** (saved for app usage)
- **ABIs** used by backend (and optionally frontend)

Artifacts/exports used:
- `contracts/deployments/contract-addresses.json`
- `contracts/deployments/abis/*.json`

## 3) Smart Contracts Used (What each one does)

### 3.1 RideContract (`contracts/contracts/RideContract.sol`)

**Purpose**: Provides on-chain ride records and emits verifiable events for important ride actions.

**Existing key events**:
- `RideCreated`
- `RideJoined`
- `RideLeft`
- `RideCompleted`
- `RideCancelled`

**Blockchain enhancement we added**:
- **`RideStarted` event**
- **`startRide(uint256 rideId)` function**
- **`rideStartedAt` mapping** to store start timestamp on-chain

**How the new startRide marker works**:
- Only the ride driver can call it (`onlyDriver`)
- Only allowed once per ride (prevents multiple starts)
- Emits `RideStarted(rideId, timestamp)`

**Why it matters**:
- Adds a tamper-evident proof that the ride was actually marked “started”, useful for disputes.

---

### 3.2 DPoSGovernance (`contracts/contracts/DPoSGovernance.sol`)

**Purpose**: Maintains a set of elected delegates using a **Delegated Proof of Stake (DPoS)** mechanism.

**High-level functions** (conceptual):
- Candidate registration (with stake)
- Voting/unvoting
- Delegate selection (top-N)

**Where it is used in the application**:
- It is referenced by `DisputeResolution` contract.
- It defines who is a valid **delegate** eligible to vote on disputes.

---

### 3.3 DisputeResolution (`contracts/contracts/DisputeResolution.sol`)

**Purpose**: Creates and manages disputes for rides and allows delegates (from DPoS) to vote.

**Key feature we use**:
- `openDispute(uint256 rideId, bytes32 evidenceHash)`

**How it works in our app**:
- When a complaint is filed, the backend calls `openDispute`.
- The contract creates a new dispute and emits events.
- Later, DPoS delegates vote and the dispute can be finalized based on quorum/time.

**Why it matters**:
- Dispute creation is public and verifiable.
- Evidence is anchored as a **hash** (privacy-preserving).

---

### 3.4 Reputation / Rating Contract

**Purpose**: Provides on-chain reputation/rating logic.

**How it relates to the app**:
- Ratings can be anchored on-chain.
- The DB can store `blockchainTxHash` for auditability.

## 4) Backend ↔ Blockchain Integration (What we implemented)

Blockchain interaction is done from the backend using **ethers.js**.

### 4.1 Backend blockchain utility
- File: `server/utils/blockchain.js`

**Responsibilities**:
- Create an ethers JSON-RPC provider using `BLOCKCHAIN_RPC_URL`
- Create a wallet signer using `PRIVATE_KEY`
- Create contract instances for:
  - `RideContract`
  - `DisputeResolution`

**Inputs (from environment variables)**:
- `BLOCKCHAIN_RPC_URL`
- `PRIVATE_KEY`
- `RIDE_CONTRACT_ADDRESS`
- `DISPUTE_RESOLUTION_CONTRACT_ADDRESS`

**ABI source**:
- Reads ABI JSON from `contracts/deployments/abis/` generated by Hardhat deployment.

## 5) On-chain Features Added to App Workflows

### 5.1 Ride start anchoring (RideStarted)

**When it triggers**:
- When the driver/host starts boarding OTP in the app.

**Backend action**:
- Backend calls:
  - `RideContract.startRide(ride.blockchainRideId)`

**On-chain result**:
- Contract emits:
  - `RideStarted(rideId, timestamp)`

**Notes**:
- This is done **best-effort** (it should not break the ride flow if chain fails).

---

### 5.2 Ride completion anchoring (RideCompleted)

**When it triggers**:
- When the driver/host completes the ride from UI.

**Backend action**:
- Backend calls:
  - `RideContract.completeRide(ride.blockchainRideId)`

**On-chain result**:
- Contract emits:
  - `RideCompleted(rideId, timestamp)`

**Notes**:
- Also **best-effort**, to keep UX smooth.

---

### 5.3 Complaint anchoring (Dispute open + evidence hash)

**When it triggers**:
- When a user files a complaint.

**Backend actions**:
1. Save complaint in DB (full details off-chain)
2. Compute `evidenceHash`
3. Call:
   - `DisputeResolution.openDispute(ride.blockchainRideId, evidenceHash)`
4. Store returned information in DB

**DB fields added for anchoring**:
- In `Complaint` model:
  - `blockchainTxHash`
  - `blockchainDisputeId`

**Security value**:
- Complaint evidence cannot be quietly modified after anchoring because the hash is immutable on-chain.

## 6) On-chain vs Off-chain Data Mapping (Important for Presentation)

### Stored in Database (off-chain)
- Full ride details, participants, statuses
- Full complaint description and metadata
- User identity info
- Admin decisions and complaint status updates

### Stored/anchored on Blockchain (on-chain)
- Ride lifecycle proofs:
  - `RideStarted` event
  - `RideCompleted` event
- Dispute creation proof:
  - `openDispute(rideId, evidenceHash)`
- (Optional) rating proof via reputation contract

### Link between DB and chain
- `Ride.blockchainRideId` is the bridge between a DB ride record and the on-chain `rideId`.

---

## 7) Key Management (Blockchain keys)

### What key is used
- Backend uses `PRIVATE_KEY` to sign transactions on behalf of the system (local Hardhat).

### Where it is stored
- Stored in environment variables (`.env`), not in code.

### Best practices
- Never commit `.env` to Git.
- Use Hardhat test accounts only for local development.
- For production: use separate wallets, secret manager, and rotate keys.

## 8) Summary (What to say in 20 seconds)

- We deployed smart contracts on local Hardhat.
- We added `RideStarted` and used `RideCompleted` events for tamper-evident ride lifecycle proofs.
- We anchored complaints by opening disputes on-chain with an evidence hash.
- Dispute decisions are decentralized using DPoS delegates (via governance contract).
- The DB holds full data; blockchain holds only integrity proofs and governance actions.
